# 00. 시작하기 전에: 인덱스가 왜 빠른가

실험을 시작하기 전에 꼭 알아야 할 것만 **아래에서부터 한 단계씩** 정리했습니다.
한 번에 다 외울 필요는 없어요. 실험하다가 막히면 해당 단계로 돌아오면 됩니다.

---

## 1단계. 데이터는 디스크에 "페이지" 단위로 저장된다

- 테이블의 행들은 결국 **디스크 파일**에 저장됩니다.
- MySQL(InnoDB)은 디스크를 한 행씩 읽지 않고, **16KB 크기의 묶음(페이지)** 단위로 읽고 씁니다.
  - 책으로 치면 "한 글자씩"이 아니라 "한 쪽씩" 읽는 것입니다.
- 한 번 읽은 페이지는 **메모리(버퍼 풀)** 에 올려 두고 재사용합니다. 메모리는 디스크보다 훨씬 빠릅니다.
  - 이 실습의 버퍼 풀은 1GB입니다 (`mysql/conf.d/lab.cnf`).

> 그래서 DB 성능의 핵심은 **"페이지를 몇 개 읽느냐"** 입니다. 읽는 행·페이지가 적을수록 빠릅니다.

## 2단계. 인덱스가 없으면: 처음부터 끝까지 다 본다 (풀스캔)

```sql
SELECT * FROM products WHERE seller_id = 500;
```

`seller_id`가 500인 상품이 어디 있는지 모르니, **20만 행을 처음부터 끝까지 전부 읽으면서** 하나씩 비교합니다.
이것을 **풀 테이블 스캔(Full Table Scan)** 이라고 하고, 실행 계획에는 `type = ALL` 로 나옵니다.

- 결과가 100건이어도 20만 건을 다 읽습니다.
- 데이터가 10배 늘면 시간도 대략 10배 늘어납니다.

→ **E01** 에서 직접 확인합니다.

## 3단계. 인덱스 = 정렬된 "찾아보기"

책 맨 뒤의 찾아보기(색인)를 떠올려 보세요.

```
가비지 컬렉션 ...... 132쪽
인덱스 ............ 45쪽, 210쪽
트랜잭션 .......... 88쪽
```

- 단어가 **가나다순으로 정렬**되어 있어서 원하는 단어를 금방 찾습니다.
- 단어 옆에 **쪽 번호(위치)** 가 있어서 본문으로 바로 갑니다.

DB 인덱스도 같습니다.

```
seller_id  →  행의 위치(PK)
   1       →  id 17, id 230, id 512, ...
   2       →  id 8, id 99, ...
  ...
  500      →  id 1203, id 4410, ...      ← 여기만 보면 됨
```

`CREATE INDEX idx_products_seller ON products (seller_id);` 를 실행하면
MySQL이 `seller_id` 기준으로 **정렬된 목록을 따로 하나 더** 만들어 둡니다.

## 4단계. 정렬된 목록을 빨리 찾는 구조: B-tree

정렬만 되어 있어도 "가운데부터 펼쳐서 반씩 줄여 나가기(이진 탐색)"가 가능합니다.
MySQL은 이걸 디스크에 맞게 만든 **B-tree(B+tree)** 구조를 씁니다.

```
                [ 루트 페이지 ]
               /       |       \
     [ 1 ~ 300 ]  [ 301 ~ 700 ]  [ 701 ~ 1000 ]     ← 중간 페이지
       /  |  \         |
   [리프][리프]...  [ 480 ~ 520 ]                   ← 리프 페이지: 실제 값 + 위치
```

- 한 페이지(16KB)에 수백 개의 키가 들어가서, **수백만 건이어도 보통 3~4단계만 내려가면** 원하는 값에 도착합니다.
- 리프 페이지끼리는 **순서대로 연결**되어 있어서 "500부터 600까지"(범위)나 "최신순으로 20개"(정렬)도 옆으로 쭉 읽으면 됩니다.

> 인덱스는 **"찾기(탐색)"** 와 **"정렬된 순서로 읽기"** 두 가지를 빠르게 해 줍니다.
> 자료의 표현으로는 "특정 쿼리 패턴의 탐색·정렬 비용을 줄이는 자료구조"입니다.

## 5단계. InnoDB만의 특징: 테이블 자체가 PK 순서로 정렬되어 있다

여기가 처음엔 헷갈리는 부분입니다.

- InnoDB 테이블은 **PRIMARY KEY 순서로 정렬된 B-tree 그 자체**입니다. (클러스터드 인덱스라고 부릅니다)
  - 그래서 `WHERE id = 123` 은 인덱스를 따로 만들지 않아도 항상 빠릅니다. (실행 계획 `type = const`)
- 우리가 추가로 만드는 인덱스(보조 인덱스)의 리프에는 **"인덱스 컬럼 값 + PK 값"** 이 들어 있습니다.

그래서 보조 인덱스로 찾을 때는 **두 번 찾습니다.**

```
① 보조 인덱스(seller_id)에서 500 찾기 → PK 목록 [1203, 4410, ...]
② PK 로 테이블(클러스터드 인덱스)에 다시 가서 name, price 등 나머지 컬럼 읽기
```

②번을 결과 행 수만큼 반복하기 때문에, **결과가 아주 많으면** 오히려 처음부터 쭉 읽는 풀스캔이 더 쌀 수도 있습니다.
→ **E03** 에서 실제로 이런 일이 생기는지 확인합니다.

## 6단계. 커버링 인덱스: 두 번째 찾기를 건너뛰기

조회하는 컬럼이 **전부 인덱스 안에 있으면** ②번이 필요 없습니다.

```sql
-- 인덱스 (status, created_at, id) 가 있을 때
SELECT id, created_at FROM posts WHERE status = 'PUBLISHED' ...   -- 인덱스만 보고 끝 (커버링)
SELECT *              FROM posts WHERE status = 'PUBLISHED' ...   -- 행마다 테이블에 다시 가야 함
```

실행 계획 `Extra` 에 **`Using index`** 가 보이면 커버링입니다.
→ **E07**

## 7단계. 복합 인덱스: 전화번호부처럼 "왼쪽부터" 정렬

`(성, 이름)` 순서로 정렬된 전화번호부를 생각해 보세요.

| 찾는 방법 | 빠른가? |
|---|---|
| 성 = '김' | ✅ '김' 부분만 펼치면 됨 |
| 성 = '김' AND 이름 = '철수' | ✅ '김' 안에서 다시 '철수' |
| 이름 = '철수' (성 모름) | ❌ 모든 성을 다 뒤져야 함 |

복합 인덱스 `(a, b, c)` 도 마찬가지로 **a로 먼저 정렬, 같은 a 안에서 b로 정렬...** 되어 있습니다.
그래서 `a`, `a+b`, `a+b+c` 조건에는 잘 쓰이지만 `b` 만으로는 잘 쓰이지 않습니다.
→ **E04** (왼쪽부터), **E06** (어떤 컬럼을 앞에 둘지)

## 8단계. 선택도: 인덱스로 "얼마나 많이 걸러지나"

- `email` 은 사람마다 다름 → 한 값으로 1건만 남음 → **선택도가 높다** → 인덱스 효과 큼
- `status` 는 3종류뿐이고 90%가 `PUBLISHED` → 한 값으로 90%가 남음 → **선택도가 낮다** → 인덱스 효과 작음

"WHERE 에 나오니까 인덱스"가 아니라, **그 조건으로 얼마나 줄어드는지**를 봐야 합니다.
→ **E03**

## 9단계. 옵티마이저: 어떤 방법으로 읽을지 MySQL이 고른다

인덱스를 만들었다고 무조건 쓰는 것이 아닙니다.
MySQL의 **옵티마이저**가 통계(행 수, 값 분포)를 보고 "풀스캔 vs 인덱스 A vs 인덱스 B" 중 **비용이 가장 싸 보이는 방법**을 고릅니다.

- 그 계획을 보여주는 것이 **`EXPLAIN`** (예상)
- 실제로 실행하고 결과를 보여주는 것이 **`EXPLAIN ANALYZE`** (실제)
- 옵티마이저도 틀릴 수 있습니다. 그래서 **예상(EXPLAIN)과 실제(측정)를 둘 다** 봐야 합니다.

→ [01_실행계획_읽는법.md](01_실행계획_읽는법.md)

## 10단계. 인덱스는 공짜가 아니다

인덱스는 "정렬된 목록을 하나 더" 갖는 것이라서,

- **저장 공간**을 차지하고 (메모리 버퍼 풀도 나눠 씀)
- INSERT / UPDATE / DELETE 때마다 **그 목록도 같이 고쳐야** 합니다.

인덱스가 5개면 행 하나를 넣을 때 B-tree 6개(테이블 + 인덱스 5개)를 고칩니다.
→ **E11** 에서 인덱스 개수에 따라 INSERT가 얼마나 느려지는지 측정합니다.
