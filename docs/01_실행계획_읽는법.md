# 01. 실행 계획 읽는 법 (EXPLAIN / EXPLAIN ANALYZE)

`make bench` 와 `make explain` 은 두 가지를 같이 보여 줍니다.

| 도구 | 무엇을 보여주나 | 주의 |
|---|---|---|
| `EXPLAIN` | 옵티마이저가 **"이렇게 읽을 계획"** 이라고 정한 방법과 **예상** 행 수 | 실제로 실행하지 않음. 숫자는 추정치 |
| `EXPLAIN ANALYZE` | **실제로 실행**해 보고, 단계별 실제 시간·실제 행 수 | 쿼리를 진짜로 실행함 (운영 DB에서는 부하 주의) |

---

## 1. EXPLAIN 표 읽기

E01 을 인덱스 없이 실행했을 때의 실제 출력입니다.

| id | select_type | table | type | possible_keys | key | key_len | ref | rows | filtered | Extra |
|---|---|---|---|---|---|---|---|---|---|---|
| 1 | SIMPLE | products | **ALL** | NULL | **NULL** | NULL | NULL | **199002** | 1.0 | Using where |

`(seller_id, status)` 인덱스를 만든 뒤:

| id | select_type | table | type | possible_keys | key | key_len | ref | rows | filtered | Extra |
|---|---|---|---|---|---|---|---|---|---|---|
| 1 | SIMPLE | products | **ref** | idx_products_seller_status | **idx_products_seller_status** | 90 | const,const | **112** | 100.0 | NULL |

처음에는 **`type`, `key`, `rows`, `Extra` 네 칸만** 보면 충분합니다.

### type: 어떻게 찾아가는가 (위쪽일수록 보통 좋음)

| type | 뜻 | 비유 |
|---|---|---|
| `const` | PK나 UNIQUE로 딱 1건 | 주민번호로 사람 찾기 |
| `eq_ref` | 조인할 때 상대 테이블에서 PK/UNIQUE로 1건씩 | |
| `ref` | 인덱스로 같은 값(=)인 것들 찾기 | 찾아보기에서 "인덱스" 항목 펼치기 |
| `range` | 인덱스로 범위(`<`, `BETWEEN`, `LIKE 'abc%'`) 읽기 | 찾아보기에서 "ㅇ~ㅈ" 구간 읽기 |
| `index_merge` | 인덱스 여러 개를 따로 읽고 합치기 | E09 의 OR 조건 |
| `index` | **인덱스 전체**를 처음부터 끝까지 | 찾아보기를 첫 장부터 끝까지 다 읽기 |
| `ALL` | **테이블 전체**를 처음부터 끝까지 (풀스캔) | 책 본문을 첫 장부터 끝까지 다 읽기 |

> ⚠️ `index` 는 이름 때문에 좋아 보이지만 "인덱스를 **전부** 읽는다"는 뜻입니다. 테이블보다는 작아서 `ALL` 보다는 낫지만, 찾는 게 아니라 훑는 것입니다. (E09 의 `LIKE '%...%'`)

### key: 실제로 고른 인덱스

- `possible_keys`: 쓸 수 **있는** 후보
- `key`: 실제로 **고른** 인덱스. `NULL` 이면 인덱스를 안 씀
- 후보에는 있는데 `key` 가 `NULL` 이면 → "있는데 안 쓴" 상황. 이유를 찾아야 함 (E09 형변환)

### key_len: 인덱스의 몇 번째 컬럼까지 썼나

복합 인덱스에서 **앞에서부터 몇 바이트를 썼는지**입니다. 컬럼별 크기를 알면 몇 개 컬럼을 썼는지 알 수 있습니다.

| 컬럼 타입 | key_len |
|---|---|
| `BIGINT NOT NULL` | 8 |
| `INT NOT NULL` | 4 |
| `DATETIME NOT NULL` | 5 |
| `VARCHAR(20) NOT NULL` (utf8mb4) | 20 × 4 + 2 = 82 |

예: `(seller_id BIGINT, status VARCHAR(20))` 를 둘 다 쓰면 8 + 82 = **90**. 위 표의 key_len 90 이 바로 그것입니다.
`(seller_id, status, created_at, ...)` 에서 세 컬럼까지 쓰면 8 + 82 + 5 = **95** (E06).

### rows / filtered: 몇 행을 읽을 것 같은가 (추정)

- `rows`: 이 단계에서 읽을 것으로 **예상한** 행 수
- `filtered`: 그중 조건을 통과할 것으로 예상한 비율(%)
- 둘 다 **통계 기반 추정치**입니다. 실제 값은 EXPLAIN ANALYZE 나 측정 결과의 "훑은 항목"으로 확인하세요.

### Extra: 추가 정보 (중요한 것만)

| Extra | 뜻 | 좋은가? |
|---|---|---|
| `Using where` | 읽은 행을 WHERE 조건으로 한 번 더 거름 | 보통. `ALL` 과 같이 나오면 "다 읽고 거름" |
| `Using index` | **커버링 인덱스**: 테이블에 안 가고 인덱스만으로 끝 | 👍 |
| `Using index condition` | **ICP**: 인덱스 안에서 먼저 조건 검사 후 테이블 접근 | 👍 대체로 좋음. 단 인덱스를 많이 훑고 있을 수도 있음 (E06) |
| `Using filesort` | 인덱스 순서를 못 써서 **따로 정렬** | 👎 행이 많으면 비쌈 (E05) |
| `Using temporary` | 중간 결과용 임시 테이블 생성 | 👎 GROUP BY, UNION 등 |
| `Backward index scan` | 인덱스를 **거꾸로** 읽음 (DESC 정렬) | 👍 정렬 없이 최신순 처리 |
| `Using index for skip scan` | 복합 인덱스의 앞 컬럼을 건너뛰며 사용 (MySQL 8.0.13+) | 상황에 따라 (E04 더 해보기) |
| `Using union(a,b)` | 인덱스 두 개 결과를 합침 (index_merge) | 상황에 따라 (E09) |

## 2. EXPLAIN ANALYZE 읽기

E06 에서 "범위 컬럼을 앞에 둔 인덱스"를 쓸 때의 실제 출력입니다.

```
-> Limit: 20 row(s)  (cost=20277 rows=20) (actual time=42.9..42.9 rows=20 loops=1)
    -> Index range scan on products using idx_products_created_seller_status_id
         over (created_at < '2025-06-01 00:00:00') (reverse),
         with index condition: ((products.status = 'ON_SALE') and (products.seller_id = 500) ...)
         (cost=20277 rows=99501) (actual time=42.9..42.9 rows=20 loops=1)
```

### 읽는 순서: 안쪽(들여쓰기가 깊은 쪽)부터

트리 구조라서 **가장 안쪽 줄이 먼저 실행**되고, 그 결과가 바깥 줄로 올라갑니다.
위 예시는 ① 인덱스를 범위로 거꾸로 읽고 → ② 20개가 되면 멈춤(Limit) 입니다.

### 괄호 두 개의 의미

| 부분 | 뜻 |
|---|---|
| `(cost=20277 rows=99501)` | **예상**: 비용, 예상 행 수 (EXPLAIN 과 같은 정보) |
| `(actual time=42.9..42.9 rows=20 loops=1)` | **실제**: 첫 행이 나온 시각(ms)..마지막 행이 나온 시각(ms), 실제로 내보낸 행 수, 반복 횟수 |

- `actual time=A..B`: 이 단계가 시작해서 **첫 행을 내보내기까지 A ms, 전부 끝나기까지 B ms**
- `rows`: 이 단계가 **위로 넘겨준** 행 수 (훑은 행 수가 아님!)
- `loops`: 이 단계가 몇 번 반복됐는지. 조인의 안쪽 테이블은 `loops` 가 바깥 행 수만큼 커집니다. 총 행 수 = rows × loops

### 함정: "rows=20 인데 왜 43ms나 걸렸지?"

`rows` 는 **위로 넘긴** 행 수라서, 인덱스 안에서 조건을 검사하고 **버린 항목**은 보이지 않습니다.
위 예시는 실제로 인덱스 항목을 약 17만 개 검사하고 20개만 넘겼습니다.
그래서 이 레포의 측정 도구는 **"엔진이 훑은 행·인덱스 항목 수"** 를 따로 세어 줍니다 → [02_측정_원칙.md](02_측정_원칙.md)

### 예상과 실제가 크게 다르면

`rows=99501`(예상) vs `rows=20`(실제)처럼 차이가 크면 다음을 의심합니다.

- `LIMIT` 때문에 일찍 멈춘 경우 (위 예시가 이 경우, 정상)
- 통계가 오래됨 → `ANALYZE TABLE 테이블명;`
- 데이터 분포가 한쪽으로 쏠림 (특정 판매자에 상품이 몰림 등)

## 3. 체크리스트 (자료 5장, 9-3)

인덱스 전후로 이 다섯 가지를 비교해서 기록하세요.

1. **의도한 인덱스를 선택했는가?** → `key`
2. **테이블 전체 스캔이나 넓은 범위 스캔이 줄었는가?** → `type`, 훑은 항목 수
3. **별도 정렬(filesort)이 사라졌는가?** → `Extra`
4. **예상 행 수와 실제 행 수 차이가 큰가?** → `rows` vs `actual ... rows`
5. **같은 데이터·파라미터·환경에서 실제 시간이 얼마나 달라졌는가?** → 측정 결과 p95
