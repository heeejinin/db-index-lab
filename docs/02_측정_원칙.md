# 02. 측정 원칙: "빨라졌다"를 믿을 수 있게 말하는 법

자료 9-4: *"성능 수치는 반드시 측정 조건과 함께 제시합니다. 실제로 측정한 수치만 넣고, 단일 실행 한 번의 결과를 일반화하지 않습니다."*

이 문서는 측정 도구(`make bench`)가 **무엇을 어떻게 재는지**와, 측정할 때 지킬 규칙을 정리합니다.

---

## 1. `make bench` 가 하는 일

```
1) 워밍업 5회       → 데이터를 메모리(버퍼 풀)에 올려서 "첫 실행만 느린" 효과 제거
2) 측정 30회        → 매번 시간을 잼
3) 통계 계산        → 평균, p50, p95, p99, 최소, 최대
4) 한 번 더 실행    → 엔진이 훑은 행·인덱스 항목 수를 셈
5) EXPLAIN, EXPLAIN ANALYZE 실행
6) 결과 저장        → results/<실험>/<쿼리>__<라벨>__<시각>.md / .json
```

쿼리 파일 맨 위에 `-- @runs 15` 처럼 적거나, `ARGS='--runs 50'` 으로 횟수를 바꿀 수 있습니다.
풀스캔처럼 1번에 1초 넘게 걸리는 쿼리는 `@runs` 를 작게 잡아 두었습니다.

## 2. 출력 숫자의 의미

### 시간 (ms)

| 줄 | 뜻 |
|---|---|
| **서버 실행** | MySQL 안에서 쿼리를 실행한 시간 (performance_schema 의 `TIMER_WAIT`). **DB 자체의 성능**을 볼 때 이 값을 기준으로 |
| 클라이언트 | 측정 도구가 보낸 순간부터 결과를 다 받을 때까지. 네트워크와 결과 전송 시간 포함. 결과 행이 많으면 서버 실행보다 꽤 커짐 |

### 평균 vs p95 vs p99

30번 측정한 값을 **작은 것부터 줄 세웠다고** 생각해 보세요.

- **p50 (중앙값)**: 딱 가운데 값. "보통 이 정도"
- **p95**: 앞에서 95% 위치의 값. "100번 중 95번은 이것보다 빠르다"
- **p99**: 앞에서 99% 위치의 값. 측정이 30회면 사실상 최댓값과 같습니다
- **평균**: 한두 번 튀는 값에 끌려가기 쉬움

자료 5장처럼 **"평균 20ms 개선"보다 "p95 가 X ms → Y ms"** 로 말하는 연습을 하세요.
사용자가 체감하는 느림은 평균이 아니라 꼬리(p95, p99)에서 나옵니다.

### 읽은 행 수: 세 가지 숫자

| 숫자 | 출처 | 특징 |
|---|---|---|
| `rows_examined` | performance_schema | 슬로우 쿼리 로그에도 나오는 값. **인덱스 안에서 걸러져 버려진 항목(ICP)은 세지 않음** |
| 결과 행 수 / `rows_sent` | | 클라이언트로 보낸 행 |
| **엔진이 훑은 행·인덱스 항목 수** | `Handler_read_*` + InnoDB ICP 카운터 | 테이블 행이든 인덱스 항목이든 **실제로 훑은 개수**. 이 레포에서 가장 정직한 "일의 양" |

"엔진이 훑은 항목" 옆에는 내역이 나옵니다.

| 내역 | 뜻 |
|---|---|
| 테이블 순차 스캔(풀스캔) | `Handler_read_rnd_next`. 이 숫자가 테이블 행 수만큼 크면 풀스캔 |
| 인덱스로 위치 찾기 | `Handler_read_key`. B-tree 를 위에서부터 내려간 횟수 |
| 인덱스 순서대로 다음 행 / 역순으로 이전 행 | `Handler_read_next` / `_prev`. 인덱스를 옆으로 쭉 읽은 개수 (범위, 정렬) |
| 위치로 행 다시 읽기 | `Handler_read_rnd`. 정렬 후 행을 다시 읽는 경우 등 |
| 인덱스 안에서 검사 후 버림(ICP) | `Using index condition` 으로 인덱스에서 조건을 보고 버린 항목 |

> 💡 **시간은 내 맥 상태에 따라 흔들리지만, 훑은 항목 수는 거의 흔들리지 않습니다.**
> 그래서 전후 비교를 할 때 "시간"과 "훑은 항목 수"를 **같이** 기록하세요. 둘이 같은 방향으로 움직이면 결론을 믿을 수 있습니다.

ICP 카운터는 서버 전체 값이라서, 측정 중에 DBeaver 등으로 다른 쿼리를 돌리면 숫자가 섞일 수 있습니다.

## 3. 측정 규칙 7가지

1. **한 번에 하나만 바꾼다.** 인덱스를 바꿀 때는 쿼리·파라미터·데이터를 그대로 둔다.
2. **같은 파라미터로 비교한다.** `sellerId=500` 으로 전을 쟀으면 후도 500. 다른 값은 라벨을 따로 붙여서 추가로 잰다.
3. **워밍업 후에 잰다.** (도구가 자동으로 함) 대신 "처음 한 번은 느리다"는 사실도 알아 두기.
4. **실험 사이에 `make reset-indexes`.** 앞 실험의 인덱스가 남아 있으면 결과가 섞인다. `make status` 로 현재 인덱스를 확인하는 습관.
5. **측정 중에는 다른 무거운 작업을 하지 않는다.** (빌드, 영상, 다른 쿼리)
6. **조건을 함께 기록한다.** 데이터 규모(SCALE), 파라미터, 횟수, 워밍업 여부. 결과 `.md` 에 자동으로 남는다.
7. **이상하면 다시 잰다.** p95와 p50이 크게 벌어지거나 결과가 예상과 반대면 한 번 더 재서 재현되는지 본다.

## 4. 캐시를 비우고 재고 싶다면 (콜드 캐시)

워밍업을 한 값은 "데이터가 메모리에 올라온 상태"입니다. 메모리가 빈 상태(서버를 막 켰을 때)를 보고 싶다면:

```bash
make down && make up
make bench Q=... L=cold ARGS='--warmup 0 --runs 1'
```

첫 실행이 얼마나 느린지 비교해 보면 버퍼 풀의 효과를 체감할 수 있습니다.

## 5. 이 도구의 한계 (솔직하게)

- **혼자서 하나씩** 실행합니다. 실제 서비스처럼 **동시에 여러 요청**이 들어올 때의 락 경합, 커넥션 부족 등은 볼 수 없습니다.
  → 자료의 K6 부하 테스트(동시 사용자, RPS, p95/p99)는 API 서버가 필요해서 이 4주 범위에서 뺐습니다. 이후 락·트랜잭션 학습 때 Spring API + K6 로 확장하면 좋습니다.
- 내 맥 · Docker 안에서 잰 값입니다. **운영 서버의 절대 수치로 일반화하지 않습니다.** 대신 "같은 조건에서 몇 배 차이"와 "훑은 항목 수"는 의미 있는 근거입니다.
- 쓰기 실험(E11)은 매번 ROLLBACK 하므로 "롤백 직전까지의 INSERT 시간"만 잽니다.
